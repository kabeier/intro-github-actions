Mental model: GitHub Actions is your local workflow, repeated in a clean environment.

run-tests.yml, on a dev branch

name: Run Test Suite

on:
  push:
    branches:
      - dev

  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 18
      - name: Install dependencies
        run: npm install

      - name: Install Jest
        run: npm install jest

      - name: Run tests
        run: |
          npm test || (echo "❌ Tests failed" && exit 1)
git checkout -b dev
git add .
git commit -m "Run tests in CI"
git push -u origin dev

Your own projects: Jest in package.json (--save-dev), so npm install gets it. No Install Jest step.

** CODE ALONG, about 5 minutes. ** New file .github/workflows/run-tests.yml (ci-factorial is a new repo, so this is its only workflow). Students copy from Code Lab 2; the YAML is the curriculum's, word for word.

  • | = "the next lines are one multi-line command".
  • npm test || (…exit 1): if the tests fail, print ❌ and fail the step.
  • Push to dev → Actions tab: Run Test Suite starts. (The demo repo also shows a Hello World run: it has both files. Students' ci-factorial doesn't.)
  • Install Jest step: it's there because the lesson's package.json doesn't list Jest. Students ran npm install --save-dev jest on slide 3, so their package.json lists it: npm install already installs Jest, and this step is harmless. Their log says "added … packages", not "up to date" like slide 6.
  • Say: "In your own projects, put Jest in devDependencies with npm install --save-dev jest and drop this step. npm install gets it from there." Better practice: one list of what the project needs, and the same Jest version on your laptop and in CI.

"What's the @v4?" uses: actions/checkout@v4 = run the code in the repo github.com/actions/checkout, at its tag v4. Same idea as a Docker tag: node:18.

@mainwhatever is newest today. Avoid: can break any timenode:latest
  • How to pick: the action's Marketplace page or its repo's Releases → use the newest major (the number after v).
  • Why v4 here: it's the curriculum's YAML, and it still works. Today (Oct 2026) the newest is v7 for checkout and setup-node.
  • They will see a yellow warning on the run: "Node.js 20 is deprecated … actions/checkout@v4 … forced to run on Node.js 24" (seen on the demo repo). A warning, not an error: the run is still green. In their own projects, a newer major makes it go away.
  • Say: "@v4 is like a Docker tag. It picks which version of someone else's code runs. Use the newest major from the action's Releases page."

Run it again without a new commit

on:
  push:
    branches:
      - dev
  pull_request:
    branches:
      - main
  workflow_dispatch:
  • workflow_dispatch = "can be started by hand". The workflow's page gets a Run workflow button
  • Any finished run also has Re-run all jobs (top right)
  • Use them to re-check a flaky failure or debug the workflow, without junk commits

Without it, GitHub refuses: "Workflow does not have 'workflow_dispatch' trigger".

  • Recap: students added workflow_dispatch to hello-world.yml in Lecture 1 (slides 13 and 15). New here: using it on the real test workflow, and Re-run all jobs.
  • The Run workflow button appears once the workflow with workflow_dispatch is on the default branch (main). Merge first, then show it.
  • Tested: before adding the trigger, starting it by hand failed with that exact message (HTTP 422).

Workflows are code

  • Edit them in your editor, commit them, keep their history
  • Change them on a feature branch, open a pull request, get a review
  • Don't assume a workflow works: watch its first run

A broken workflow can let broken code through. Review it like code.

Cheat sheet: a workflow file

name: CI                  # Actions tab label

on:                       # WHEN it runs
  push:
    branches: [dev]       # same as - dev
  pull_request:
    branches: [main]      # the PR's target
  schedule:
    - cron: "0 0 * * *"   # daily, 00:00 UTC
  workflow_dispatch:      # Run workflow button

env:                      # variables
  NODE_ENV: test          # for every job
jobs:
  test:                         # job id = check name
    runs-on: ubuntu-latest      # WHERE
    steps:                      # HOW, in order
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:                   # inputs to the action
          node-version: 18
      - run: npm install        # a terminal command
      - name: Run tests         # label in the log
        run: |                  # several lines
          npm test
          echo "done"

  deploy:
    needs: test                 # waits for test ✓
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying"

Indent = "belongs to". Every key lives in one of these spots.
