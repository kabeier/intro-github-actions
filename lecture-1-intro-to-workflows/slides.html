Programming a robot: exact instructions

  • A workflow is a recipe GitHub follows every time something happens in your repo
  • The robot does only what you wrote, in order. Nothing else.
  • Like the peanut-butter-and-jelly "exact instructions" challenge: forget "open the jar" and there's no sandwich

Why every team uses this

  • Automated testing: on every change, not when someone remembers
  • Early bug detection: before it reaches production
  • Team confidence: refactor and collaborate without fear
  • Same environment for everyone
  • Fast feedback: a failure shows up in minutes

A normal day at work

  1. You open a pull request
  2. GitHub runs the tests automatically
  3. The team reviews the code and the results
  4. Only passing code is merged

In professional teams, code is rarely merged without checks passing.

"Workflows are no longer optional. Employers expect you to read a red ✗ and fix it."

Other common uses: linting/formatting, building Docker images, deploying after tests pass.

YAML in three rules

name: Hello World Workflow   # key: value

jobs:
  say-hello:                 # 2 spaces in = inside
    steps:
      - name: Print a message  # - = an item in a list
        run: echo "Hi"
  1. key: value (space after the colon)
  2. Indent with spaces, never tabs. Indenting = "belongs to"
  3. - starts a list item

Wrong indentation = "Invalid workflow file". The robot can't even read it.

"Dockerfiles were one instruction per line. YAML is a tree: indentation is the structure."

VS Code shows indentation guides. Two spaces per level is the convention.

hello-world.yml

name: Hello World Workflow

on:
  push:

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - name: Print a message
        run: echo "Hello from GitHub Actions!"
  • name: anything; name it after its job
  • on: push: every push, any branch (no branch listed)
  • jobs → say-hello: one task
  • runs-on: the machine, a fresh Ubuntu
  • steps: labeled commands; run = a terminal command
git add .   ·   git commit -m "Add hello world workflow"   ·   git branch -M main   ·   git remote add origin https://github.com/YOUR-USERNAME/hello-actions.git   ·   git push -u origin main

"Does on: match?" On every push or PR, GitHub opens every file in .github/workflows/ and asks: is this event listed under on:? If branches are listed, is it one of them? Yes → a runner runs the file. No → skipped, nothing in the Actions tab.

on: decides when the robot works

You want…on:Typical use
only one branch
on:
  push:
    branches:
      - main
deploy only what's on main
check pull requests
on:
  pull_request:
    branches:
      - main
run tests before anything merges into main
on a timer
on:
  schedule:
    - cron: "0 0 * * *"
every day at midnight UTC
  • pull_request: branches: main = PRs whose target is main.
  • Cron fields: minute hour day month weekday. 0 0 * * * = 00:00 UTC daily (that's 7 or 8 pm Eastern the evening before).
  • Why conditions matter: fewer pointless runs, lower cost, matches your git strategy, no accidental deploys.

Try it: a branch filter

1 · Change the trigger, then push to main

on:
  push:
    branches:
      - main
git commit -am "Only run on main"
git push

2 · Now push a different branch

git checkout -b try-filter
echo "test" >> notes.txt
git add .
git commit -m "Change on a branch"
git push -u origin try-filter

Actions tab: a run for main, and nothing for try-filter.

No run is the correct result: the filter said main only.
